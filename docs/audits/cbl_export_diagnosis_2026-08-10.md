# CBL export diagnosis

## Scope and conclusion

This audit is against PrismaQuant commit `76666bd6ce17cd5ffb0d9092804705bdad7205a8` and the Gridbook release pinned by `prismaquant/gridbook_runtime/gridbook_runtime_pin.json:1-6`, commit `9f915dd868eab2e13ab7847a67c594e2c5c8955c`. No CUDA or serving run was performed.

The low-level statement “the exporter cannot emit learned books” is not literally true at this revision. Both direct exporters have a research learned-book path, and the existing CPU test writes, reloads, and decodes a learned `.pqcb` sidecar; that path is explicitly unstamped research and records that its render identity was not verified (`prismaquant/export_nvfp4_cb.py:785-869`, `prismaquant/export_nvfp4_cb_streaming.py:2707-2788`, `tests/test_nvfp4_cb_formats.py:574-645`). The measured production observation remains explained: the pipeline and allocator reject learned books, the cost/cache producers have no value-bearing learned-book input, and the research exporter trains the wrong sharing recipe too late to establish the immutable cost/KL/cache/export identity (`prismaquant/run-pipeline.sh:88-110`, `prismaquant/allocator.py:1980-1988`, `prismaquant/measure_quant_cost.py:75-87`, `prismaquant/production_weight_cache.py:3247-3258`).

There is also a fail-closed serving blocker, but it is specific to learned books on routed-MoE stacks. Pinned Gridbook really does pass a LUT into individual kernel launches, but its uniform routed-MoE loader resolves one scheme and one LUT for the fused `w13` and `w2` stacks, while the certified CBL recipe learns distinct books for gate, up, and down (`/home/rob/gb-release-prep/gridbook/config.py:1339-1374`, `/home/rob/gb-release-prep/gridbook/moe.py:458-505`, `/home/rob/gb-release-prep/gridbook/moe.py:1894-1946`, `tools/dsv4_cbl_kernels.py:10-19`). Emitting distinct refs through that routed path could load successfully and then decode indices against the wrong table, so PrismaQuant must refuse learned refs on routed stacks until the runtime ABI changes (`/home/rob/gb-release-prep/gridbook/config.py:1364-1374`, `/home/rob/gb-release-prep/gridbook/moe.py:500-505`, `/home/rob/gb-release-prep/gridbook/moe.py:1915-1946`).

That routed blocker does **not** block dense CBL. The dense loader already looks up `codebook_ref` inside its per-role loop, interns every distinct ref tuple, constructs a per-row `cb_row_offset`, and asserts that the offset covers the fused output (`/home/rob/gb-release-prep/gridbook/linear.py:374-445`). Distinct gate/up refs inside a dense `gate_up_proj`, and q/k/v refs inside a dense `qkv_proj`, therefore need producer plumbing but no Gridbook change. The safe producer scope is: enable value-bearing learned books for dense FP8-CB targets now, keep NVFP4 lattice by default, and fail closed on routed learned targets. Future MoE work remains across the immutable Gridbook pin/contract boundary (`AGENTS.md:25-43`, `docs/lanes/nvfp4-cb/MOE_LEARNED_CODEBOOK_SPEC.md:1-32`).

## 1. Where source selection stops today

### 1.1 The production identity is run-global

`CBSerializationContext` carries one scalar `codebook_source`, not a source selected per format or family (`prismaquant/nvfp4_cb_footprint.py:117-142`). Its constructor accepts only `lattice|learned`, and the environment parser reads the single `CB_CODEBOOK_SOURCE`, defaulting it to `lattice` (`prismaquant/nvfp4_cb_footprint.py:144-168`, `prismaquant/nvfp4_cb_footprint.py:660-706`, `prismaquant/nvfp4_cb_footprint.py:758-770`). The context stamp consequently writes one `codebook_source`; it emits canonical lattice hashes only when that global scalar is `lattice`, and learned content hashes only from the one global digest map (`prismaquant/nvfp4_cb_footprint.py:396-470`). Physical default refs and per-tensor sidecar identity branch on that same scalar (`prismaquant/nvfp4_cb_footprint.py:1498-1575`).

The config builder can represent `codebook_source` inside each individual scheme, but its public build path receives one global source and passes it to every CB scheme (`prismaquant/cb_export_config.py:613-673`, `prismaquant/cb_export_config.py:704-739`, `prismaquant/cb_export_config.py:796-810`). The render-identity validator also chooses a single lattice-versus-learned branch for the whole format scope (`prismaquant/production_weight_cache.py:2052-2089`). Therefore changing only the exporter CLI cannot express “NVFP4 lattice, FP8-CB learned” coherently across cost, cache, assignment, export config, and validation.

The appropriate source vocabulary is analogous to the existing LDLQ scope: `none|fp8|all`, with `none` meaning lattice for both families, `fp8` meaning learned only for `FP8_CB`, and `all` reserved for explicit research because NVFP4 CBL is a measured no-go. The precedent parses and stamps `PRISMAQUANT_CB_LDLQ_SCOPE=none|nvfp4|all` and resolves it per format (`prismaquant/nvfp4_cb_footprint.py:179-202`, `prismaquant/nvfp4_cb_footprint.py:374-393`, `prismaquant/nvfp4_cb_footprint.py:714-745`). To preserve the required byte-identical default, a future source-scope implementation must omit any new stamp member when the scope is `none`; adding a default-valued JSON member would change existing render identities even if rendered tensor bytes stayed unchanged (`prismaquant/nvfp4_cb_footprint.py:421-470`, `prismaquant/production_weight_cache.py:1814-1826`).

### 1.2 Production intentionally refuses learned values

For an NVFP4-CB export, the shell defaults `CB_CODEBOOK_SOURCE=lattice` and exits if it is `learned` (`prismaquant/run-pipeline.sh:88-110`). The production allocator repeats that refusal because a digest does not supply codebook values, and it separately rejects `--cb-codebook-digests` until a value-bearing bundle exists (`prismaquant/allocator.py:1980-1988`, `prismaquant/allocator.py:2252-2274`).

That explanation matches the actual render seam. Cost rendering constructs a context and calls `cb_fields_for_context` without a `codebook` argument; production cache rendering does the same (`prismaquant/measure_quant_cost.py:75-87`, `prismaquant/production_weight_cache.py:3247-3258`). The common encoder correctly raises when the effective source is learned but no exact book value was supplied (`prismaquant/nvfp4_cb_footprint.py:1070-1097`). `CB_CODEBOOK_DIGESTS` can bind bytes in identity, but the environment parser only loads a digest mapping and has no value-bearing table loader (`prismaquant/nvfp4_cb_footprint.py:660-706`, `prismaquant/nvfp4_cb_footprint.py:758-770`).

The immutable learned bundle must therefore exist before cost/cache/KL construction, and the exact tensors from that bundle must be passed to every render. Training only after allocation cannot repair the identity: render identity is built while the cache is created and already stamps the serialized-payload context (`prismaquant/production_weight_cache.py:1776-1838`).

### 1.3 The existing learned exporter is not the measured CBL producer

The direct learned exporter groups targets by the final role component and format, so e.g. the same role/rung is shared across matching layers; it then runs its generic shared trainer (`prismaquant/export_nvfp4_cb.py:113-116`, `prismaquant/export_nvfp4_cb.py:442-500`, `prismaquant/export_nvfp4_cb.py:785-833`). The streaming exporter applies the same global source and role grouping, with export-time training after assignment selection (`prismaquant/export_nvfp4_cb_streaming.py:2707-2754`).

The certified trainer instead consumes a 3-D all-expert cell, samples 64 rows per expert with seed 4321, caps at 2,000,000 vectors, and learns four FP8 product subtables for each `(layer, projection, rung)` (`tools/dsv4_cbl_kernels.py:49-53`, `tools/dsv4_cbl_kernels.py:150-177`). The original adopted arm uses one-shot scales, no scale sweep, and no LDLQ (`tools/dsv4_cbl_kernels.py:10-19`, `tools/dsv4_cbl_kernels.py:234-258`). A newer paired study uses the same certified `learn_pool` algorithm but runs both lattice and CBL with `scale_sweep=True`, specifically removing the encoder confound (`/home/rob/dq-runs/dsv4-quality-hybrid/sfd-analysis/ldlq_cbl_fp8_arm.py:16-24`, `/home/rob/dq-runs/dsv4-quality-hybrid/sfd-analysis/ldlq_cbl_fp8_arm.py:141-167`, `/home/rob/dq-runs/dsv4-quality-hybrid/sfd-analysis/ldlq_cbl_fp8_arm.py:197-217`). The study evidence therefore supports selectable one-shot and sweep-matched arms; production must stamp which arm supplied the rendered values rather than hardcoding either one.

There is still a run-global identity limitation: `scale_sweep` is one context boolean, while production FP4 layout v2 requires it to be true and the original FP8-CBL arm selects false (`prismaquant/nvfp4_cb_footprint.py:129-142`, `prismaquant/nvfp4_cb_footprint.py:222-226`, `tools/dsv4_cbl_kernels.py:10-19`). A global `True` can represent the newer sweep-matched production arm, but it cannot also make the measured one-shot FP8 arm selectable in a mixed NVFP4/FP8 artifact. A correct implementation therefore needs per-family scale-search identity, preserving the unchanged global/default stamp when no new scope is selected (`prismaquant/run-pipeline.sh:146-148`, `prismaquant/nvfp4_cb_footprint.py:421-470`).

The requested quality ceiling must be an independent production check of `K <= 43`. The current study helper says eligible through K44, which conflicts with the supplied production boundary and is not backed by the cited F1 K43/K48 crossover measurements (`tools/dsv4_cbl_kernels.py:42-66`, `/home/rob/dq-runs/dsv4-flash-0731/cost-ldlq/transfer-study-fable-verify/F1_GENERALIZATION.md:15-18`). Reusing `cbl_eligible()` would therefore violate the requirement.

## 2. What `codebook_content_digests` means

The map is keyed by each exact physical tensor name that will appear in the sidecar, not by logical role alone. Product FP8 books use names such as `cb_codebook.<ref>.FP8_CB_K28.sub0` through `.sub3`; the physical-name builder and expected subtable count are defined in `prismaquant/nvfp4_cb_footprint.py:1482-1531` and `prismaquant/cb_export_config.py:559-593`.

Each value is lowercase SHA-256 over that one tensor converted to contiguous CPU `float16`, in C order, with no framing (`prismaquant/cb_export_config.py:581-593`, `prismaquant/export_nvfp4_cb_streaming.py:2756-2765`, `/home/rob/gb-release-prep/gridbook/cb_digest.py:29-46`). The study helper's `book_sha256` is not interchangeable: it hashes all subtables sequentially as `float32`, whereas artifact provenance hashes each serialized `float16` subtable independently (`tools/dsv4_cbl_kernels.py:180-184`, `prismaquant/export_nvfp4_cb_streaming.py:2761-2765`).

For a learned identity, the producer that materializes the exact canonical FP16 tables must populate this map before stamping cost/cache/assignment identity. Stamp creation rejects an empty learned map, because a logical ref does not identify bytes (`prismaquant/nvfp4_cb_footprint.py:396-412`). Per-tensor sidecar accounting additionally requires a digest for every referenced physical subtable (`prismaquant/nvfp4_cb_footprint.py:1534-1552`), and recipe/export validation rejects missing or mismatched learned hashes (`prismaquant/nvfp4_cb_footprint.py:835-936`). Gridbook independently requires its external provenance map to cover the sidecar exactly and rejects missing, extra, or mismatched tensors (`/home/rob/gb-release-prep/gridbook/cb_digest.py:72-145`).

In a mixed lattice/learned artifact, the final external sidecar provenance must bind every serialized table, including lattice tables, because Gridbook's verifier compares the complete sidecar name set with the complete expected set (`/home/rob/gb-release-prep/gridbook/cb_digest.py:78-99`). A future per-family context must not retain the current global convention that only learned refs use `codebook_content_digests`; it must produce one complete physical sidecar digest map while still retaining canonical lattice-by-format identity in the render stamp (`prismaquant/nvfp4_cb_footprint.py:440-470`, `/home/rob/gb-release-prep/gridbook/cb_digest.py:85-114`).

## 3. Required on-disk representation

`prismaquant.cb_serialized_payload.v3` is the current JSON identity/accounting schema when the activation contract is present; min-chain uses v4 and the previous no-activation context uses v2 (`prismaquant/nvfp4_cb_footprint.py:55-88`). It is not the binary sidecar format. `layout_version=2` in the top-level producer context describes the two-tier FP4 scale layout, while an FP8-CB scheme always carries its v1 family layout because FP8 has no packed scale plane (`prismaquant/cb_layout.py:23-34`, `prismaquant/cb_layout.py:76-84`, `prismaquant/cb_export_config.py:625-646`).

The correct physical home already exists: `cb_codebooks.pqcb` is a plain safetensors file under a non-`.safetensors` extension, referenced by `codebook_file`, and omitted from vLLM's model-weight glob (`prismaquant/export_nvfp4_cb.py:1243-1250`, `prismaquant/export_nvfp4_cb.py:1351-1368`, `prismaquant/export_nvfp4_cb_streaming.py:3685-3689`, `prismaquant/export_nvfp4_cb_streaming.py:4147-4149`). Each learned book must be serialized once per exact measured `(layer, projection, rung)` ref as its four canonical contiguous FP16 subtables; expected FP8 product shapes follow the four-way bit split in `prismaquant/cb_layout.py:76-84` and `prismaquant/cb_layout.py:210-224`, and canonical tensor conversion is in `prismaquant/cb_export_config.py:581-593`.

The artifact must then connect four identities without drift: each target scheme names its exact `codebook_ref`; `quant_config.json.provenance.codebook_sha256` binds every sidecar tensor; `cb_serialized_payload` binds the same physical refs/digests used during cost and cache rendering; and the packed indices were encoded against those same table values (`prismaquant/cb_export_config.py:613-673`, `prismaquant/cb_export_config.py:769-810`, `prismaquant/nvfp4_cb_footprint.py:396-470`, `prismaquant/nvfp4_cb_footprint.py:1534-1575`). Export-time retraining is not acceptable because it can create tables different from the ones that generated the cost/cache/KL rows even if its output is well-formed (`prismaquant/allocator.py:1980-1988`, `prismaquant/production_weight_cache.py:1776-1838`).

The local layout document is stale where it calls the persisted payload schema v1; the implementation now emits v3/v4 (`docs/lanes/nvfp4-cb/LAYOUT.md:239-245`, `prismaquant/nvfp4_cb_footprint.py:55-88`). Its physical sidecar tensor naming and FP16 statement remain consistent with code (`docs/lanes/nvfp4-cb/LAYOUT.md:224-237`, `prismaquant/cb_export_config.py:559-593`).

## 4. Decoder and serving audit

### 4.1 What already works

PrismaQuant's CPU codec accepts and shape-checks explicit learned subtables, stores the resolved book in the encoded fields, reconstructs by indexing it, and echoes an explicitly loaded book through unpack (`prismaquant/nvfp4_cb_formats.py:434-483`, `prismaquant/nvfp4_cb_formats.py:3250-3276`, `prismaquant/nvfp4_cb_formats.py:3577-3658`). The existing CPU exporter test demonstrates learned encode, sidecar write/load, unpack, and bit-exact equality with emulation, but only under `allow_unstamped_research=True` and with `render_identity_verified == false` (`tests/test_nvfp4_cb_formats.py:574-645`).

Pinned Gridbook loads the named safetensors sidecar on CPU and verifies exact external hashes before use (`/home/rob/gb-release-prep/gridbook/cb_digest.py:117-145`, `/home/rob/gb-release-prep/gridbook/config.py:836-866`). It validates that a learned FP8 table is exactly E4M3-grid-valued rather than merely castable (`/home/rob/gb-release-prep/gridbook/codec.py:77-143`). Its dense loader resolves `codebook_ref` separately for every shard role, interns by the exact reference tuple rather than tensor equality, builds one `cb_row_offset` entry per output row, and asserts complete row coverage (`/home/rob/gb-release-prep/gridbook/linear.py:374-445`). Consequently different gate/up refs inside dense `gate_up_proj`, and different q/k/v refs inside dense `qkv_proj`, are already representable on pinned Gridbook. Dense FP8 decode passes the concatenated LUT and its per-row offsets to the op (`/home/rob/gb-release-prep/gridbook/linear.py:1145-1153`, `/home/rob/gb-release-prep/gridbook/ops.py:52-64`). The CUDA launcher consumes both, while the no-offset fused mid-M prefill route is marked ineligible when the loader found more than one distinct block and falls back to the exact offset-aware expansion route (`/home/rob/gb-release-prep/gridbook/linear.py:492-497`, `/home/rob/gb-release-prep/gridbook/linear.py:1205-1245`). Therefore “Gridbook dispatches a per-launch LUT” is true, and for dense fused Linears its per-row offset plus fail-closed route selection is the producer-only unlock.

### 4.2 Why that is insufficient for routed-MoE CBL

DSv4 serving fuses gate and up into a `w13` expert stack and keeps down as `w2`; PrismaQuant collapses the expanded per-expert gate/up/down assignment to the physical `gate_up_proj` and `down_proj` stacks (`prismaquant/export_nvfp4_cb_streaming.py:1141-1170`, `prismaquant/export_nvfp4_cb_streaming.py:1215-1258`). The certified book basis, however, is separate `(layer, projection, rung)` cells for gate, up, and down (`tools/dsv4_cbl_kernels.py:10-19`, `/home/rob/dq-runs/dsv4-flash-0731/cost-ldlq/transfer-study-fable-verify/F1_GENERALIZATION.md:3-18`).

For the uniform routed-MoE path, Gridbook collects all matching target schemes but compares only `grid`, `mode`, `k`, `n_sub`, `type_size`, and `activation_contract`; it does not compare `codebook_ref`, then returns the first scheme (`/home/rob/gb-release-prep/gridbook/config.py:1339-1374`). The loader consequently materializes one `scheme["codebook_ref"]` into one layer LUT (`/home/rob/gb-release-prep/gridbook/moe.py:458-505`). Both FP8 `w13` and FP8 `w2` launches receive that same `layer._cb_flat_fp8` (`/home/rob/gb-release-prep/gridbook/moe.py:1915-1920`, `/home/rob/gb-release-prep/gridbook/moe.py:1941-1946`). Different learned refs can therefore pass sidecar hash verification yet be ignored at scheme resolution, which is a silent wrong-table decode rather than a fail-closed load error (`/home/rob/gb-release-prep/gridbook/config.py:1364-1374`, `/home/rob/gb-release-prep/gridbook/cb_digest.py:72-145`).

Gridbook's mixed expert method improves granularity only to `w13` versus `w2`: it owns separate runtime groups and LUTs for those two families (`/home/rob/gb-release-prep/gridbook/moe_mixed.py:90-110`, `/home/rob/gb-release-prep/gridbook/moe_mixed.py:351-417`, `/home/rob/gb-release-prep/gridbook/moe_mixed.py:688-710`). Its wire schema has only the families `w13` and `w2`, and a CB `w13` prefix must be `gate_up_proj`, so it cannot select different gate and up books inside one fused `w13` launch (`/home/rob/gb-release-prep/gridbook/per_expert_format.py:14-48`, `/home/rob/gb-release-prep/gridbook/per_expert_format.py:170-192`).

A jointly trained gate+up book is not a valid routed workaround: it is a different, unmeasured training cell and cannot inherit the separate gate/up F1 quality result (`tools/dsv4_cbl_kernels.py:10-19`, `/home/rob/dq-runs/dsv4-flash-0731/cost-ldlq/transfer-study-fable-verify/F1_GENERALIZATION.md:3-18`). Exact routed support requires a Gridbook ABI that can select at least gate-half, up-half, and down LUT identities (or equivalent per-output-row LUT offsets), and its uniform scheme resolver must reject differing refs until that ABI is present (`/home/rob/gb-release-prep/gridbook/config.py:1364-1374`, `/home/rob/gb-release-prep/gridbook/moe.py:1915-1946`). Dense targets do not pass through this loader and are not blocked (`/home/rob/gb-release-prep/gridbook/linear.py:374-445`).

## 5. Work required for safe producer enablement

1. PrismaQuant can enable dense learned FP8-CB now by adding default-off `none|fp8|all` source scope and compatible per-family scale-search identity while preserving the exact old default stamp shape (`prismaquant/nvfp4_cb_footprint.py:396-470`, `prismaquant/nvfp4_cb_footprint.py:660-770`, `/home/rob/gb-release-prep/gridbook/linear.py:374-445`).
2. A value-bearing, content-addressed bundle must be trained with the certified per-cell algorithm before cost/cache/KL, passed verbatim into every encoder, serialized once into `.pqcb`, and limited by a measured rung policy rather than the helper's structural K44 rule (`tools/dsv4_cbl_kernels.py:42-66`, `tools/dsv4_cbl_kernels.py:150-177`, `prismaquant/measure_quant_cost.py:75-87`, `prismaquant/production_weight_cache.py:1776-1838`).
3. The producer must identify routed/stacked targets and refuse learned refs against the current Gridbook pin. It must not replace them with lattice silently, because the packed bytes and stamped learned identity would then disagree (`prismaquant/export_nvfp4_cb.py:701-726`, `prismaquant/export_nvfp4_cb_streaming.py:2600-2634`, `prismaquant/gridbook_runtime/gridbook_runtime_pin.json:1-6`).
4. The existing context-stamp and render-identity mismatch refusals must remain authoritative over the mixed per-family fields and complete sidecar digest map (`prismaquant/nvfp4_cb_footprint.py:835-936`, `prismaquant/production_weight_cache.py:2052-2089`, `prismaquant/export_nvfp4_cb_streaming.py:2789-2862`).
5. Separately, Gridbook must add and test a routed-MoE representation that preserves distinct gate/up/down refs; the current uniform and mixed schemas do not (`/home/rob/gb-release-prep/gridbook/config.py:1339-1374`, `/home/rob/gb-release-prep/gridbook/per_expert_format.py:14-48`). The TP-safe role-ref/row-offset design and served gates are specified in `docs/lanes/nvfp4-cb/MOE_LEARNED_CODEBOOK_SPEC.md:1-266`.
6. Routed behavior may be enabled only after that implementation is released with a new immutable runtime contract and PrismaQuant pin; the current pin is release `0.8.2` at commit `9f915dd...` (`prismaquant/gridbook_runtime/gridbook_runtime_pin.json:1-6`, `AGENTS.md:25-43`).

The static source audit did not and cannot establish that a changed Gridbook extension loads in the deployed vLLM build, that a full DSv4 learned artifact generates bit-exactly, that CUDA graphs retain the correct LUT selection, or that served decode/prefill throughput meets the production lane gate.
